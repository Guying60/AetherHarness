# 参赛对照实验与复现记录

## 调度对照

使用 Node.js 24.11.1 在 Windows 上运行。每种负载和策略各测五批，每批 12 个任务。两组均有三个 Agent 和三个执行槽，使用相同的能力集合、任务提交顺序和模拟执行时长。每批交替运行两种策略。其中「就绪 FIFO」按提交顺序选择首个有空闲目标 Agent 的任务，且每个任务类型固定分给主 Agent。自研策略启用优先级老化、能力匹配与负载感知。两组共用生产队列与并发计数。

| 负载 | 策略 | 完成 | 吞吐（任务/秒） | 每批耗时中位数（毫秒） | 全体排队 P95（毫秒） | 高优先级排队 P95（毫秒） |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 三类任务均衡 | 就绪 FIFO + 固定分配 | 60 | 39.97 | 300 | 234 | 105 |
| 三类任务均衡 | 自研动态调度 | 60 | 54.05 | 226 | 175 | 27 |
| 开发任务集中 | 就绪 FIFO + 固定分配 | 60 | 28.80 | 417 | 394 | 397 |
| 开发任务集中 | 自研动态调度 | 60 | 60.12 | 199 | 149 | 0 |

在开发任务集中的本地模拟负载中，自研策略将 60 个任务中的 25 个派给具备相应能力的非主 Agent，吞吐约为基线的 2.09 倍，全体排队 P95 降低约 62%。首批的 `developmentBurst-5` 是优先级为 9 的开发任务，提交后立即占用了主 Agent 的首个执行槽。与此同时，初始排队靠前的 `developmentBurst-1` 获得通用 Agent 的执行槽。毫秒级计时下的 0 表示在同一毫秒完成调度。该实验测量两种完整策略在指定任务结构下的差异，模型调用时延与产出质量由独立实验测量。原始记录包括逐任务派发和时间。[调度基准脚本](../scripts/benchmark-scheduling.mjs) · [原始记录](benchmarks/scheduling-baseline.json)

## 修复对照

三种任务共享 TTL 缓存 API 与六条固定行为断言，分别考查到期边界、覆盖写入和时间基准。一次生成预留最多 1,200 个输出 token，自修复流程每轮最多 400、最多三轮。两组使用同一个模型、温度与固定验收，反馈组把失败规则、诊断和前一候选带入下一轮。输入 token 随上下文变化并单独记录。运行输出包括每轮断言、候选散列、通过数、失败数和每个通过样本的实际 token 消耗。[修复基准脚本](../scripts/benchmark-repair.mjs)

本地脚本化样例已核对三种基线均触发预期规则，执行引擎将失败证据传给第二轮，重跑后通过全部六条断言。该样例使用已知候选进行流程验收。真实模型和 Docker 的质量、耗时与 token 对照待采样。

## Studio 复用验收

在同一 Git 提交上放置限流器和 TTL 缓存两个目标文件。对两种仓库配置执行结构相同的固定 Studio 工作流，并用可控模型响应产生首轮失败、二轮通过。两种配置均验证了审批前无 Git 交付，审批后仅生成选中目标文件的补丁，且原工作树保持干净。Git 检查真实执行，模型响应和容器执行使用测试替身。复现实验和严格 Live 启动方式见 [复现说明](../评审复现指南.md)。[Studio 回归用例](../tests/workflow-studio-tests.ts)
